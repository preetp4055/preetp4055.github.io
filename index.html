Case studies

A nightly reporting pipeline for school administrators

Target PEAK · Node.js microservices · daily reports for every level of a school system, from district down to class

Problem
Daily reports were generated once per user, even though everyone under the same part of the hierarchy saw identical content. Administrators also wanted Excel, not only PDF, and the reports had to reach them on WhatsApp.
What I did
Redesigned generation to run once per hierarchy scope instead of once per user. Added Excel (xlsx) output that shares one view model with the existing PDF path, and proved the PDF output stayed byte-identical across 13,830 test renders before changing the live path. Put generation and sending behind per-organization feature switches.
Delivery
One Excel file per scope (two sheets), sent each morning as a download link in a WhatsApp template through Wati. I chose a link over an attachment or an interactive flow so each delivery costs a single template message under WhatsApp's 2026 pricing.
Result
11,000+ reports generated and stored in S3 in a single run.

Hunting down a 145-second report timeout

Production 504s on report downloads

Problem
Report requests were timing out (504). The first suspect was slow SQL fan-out across thousands of rows.
What I did
Timed every stage of a single report: data ~1.1s, HTML ~30ms, Chrome ~2.4s. The remaining ~141s sat inside the caching wrapper: with Redis unreachable, the client queued commands offline and kept retrying for minutes before the fail-open fallback ran. I showed the earlier fan-out numbers were artifacts of the same stall, and proposed a fail-fast cache (no offline queue plus a command timeout).
Result
With the cache bypassed, the same report went from 145.1s to 3.7s, with identical output.

Taming headless Chrome for PDF generation

Batch PDF rendering with Puppeteer

Problem
PDF batches were slow, used a lot of memory and sometimes failed with 30-second navigation timeouts.
What I did
Found that the shared-browser check called a method that no longer existed in the Puppeteer version in use. The error was swallowed, so every PDF launched a new Chrome that was never closed: 32 PDFs left 32 browsers using 9.4 GB of memory. Fixed the check, and switched the page-load wait from networkidle0 to load because the report HTML has no external resources.
Result
In testing, block-level PDFs dropped from ~5s to ~1s, and the intermittent timeouts went away.

WhatsApp OTP for login and account recovery

Auth service · Wati WhatsApp Business API

Problem
OTPs went out only by SMS. The product wanted WhatsApp delivery as well, without making login fragile.
What I did
Added WhatsApp OTP delivery alongside SMS for sign-up, resend, password reset and two-factor login. The sender never throws and has a 10-second timeout, so a WhatsApp outage can't block a login. Logs mask phone numbers and never contain the OTP.
Result
When some messages seemed to be "dropped", I traced it to the provider holding broadcasts for 2–71 minutes, not to our code.
